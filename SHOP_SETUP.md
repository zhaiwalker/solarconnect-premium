# Solarconnect Store

## Хранилище и запуск

Frontend: React/TypeScript/Vite. Server: Node API, Zod validation, PostgreSQL. Vercel Functions: `api/shop.ts`, `api/page.ts`, `api/sitemap.ts`.

В локальной разработке данные сохраняются в `.solar-data/store.json` через очередь записи и атомарное переименование. Это исключительно локальный режим. На Vercel файловый режим запрещён: используется только PostgreSQL через `DATABASE_URL`. Без базы витрина работает с подбором и явным переходом в WhatsApp, не сообщает о сохранении неотправленных заявок.

Переменные из `config.env.example` задаются только на сервере. Не используйте префикс `VITE_` для секретов. `.env.local`, локальная база, тестовые данные и снимки браузера исключены из Git и деплоя.

1. Задайте `DATABASE_URL` для выделенной базы, с проверкой TLS согласно настройкам провайдера. Не отключайте проверку сертификатов.
2. Задайте случайный `ADMIN_PASSWORD` длиной не менее 16 символов.
3. Выполните `node --env-file=.env.local --import tsx scripts/init-db.ts`. Повторный запуск сохраняет данные.
4. Сохраните серверные переменные в проекте Vercel, затем опубликуйте.

База использует схему `solarconnect_private`, закрытую для PUBLIC. Таблица не должна публиковаться через Supabase Data API. Все обращения идут через сервер. Чтение/изменение состояния выполняется в транзакции с блокировкой строки; PostgreSQL сохраняет согласованность между экземплярами функций.

## Управление

`/admin`: пароль → HttpOnly, SameSite=Strict cookie с подписью, сроком 8 часов и Secure в production. Есть проверка Origin, ограничение попыток входа и заявок. Клиент не получает пароль и содержимое базы.

В панели: товары, точные SKU, характеристики, фото по HTTPS-ссылкам, цены, скидки, наличие, рекомендуемые товары, комплекты, документы и совместимость. Публикация требует заполненных данных и отметки согласования. Начальная структура содержит 24 внутренних черновика; она не выдаётся публичным API. Для модели из примера ТЗ внесены сведения из официального Datasheet Deye от 11.09.2026. Цены и наличие не генерируются.

Цена комплекта рассчитывается из цен компонентов. Компоненты нельзя удалять, пока они используются комплектом. В корзину комплект добавляется отдельными позициями. Совместимость устанавливается редактором после проверки.

Заказы и B2B-заявки видны в панели, имеют статус обработки и статус передачи в CRM. ID запроса предотвращает повторное создание. Цена, доступность, скидка и валюта заказа пересчитываются сервером; изменение цены требует нового подтверждения посетителем. Оплата на сайте не списывается.

## CRM

`CRM_WEBHOOK_URL` — HTTPS endpoint вашего адаптера. Опциональный `CRM_WEBHOOK_TOKEN` передаётся как Bearer. Сервер отправляет JSON: `id`, `kind` (`order` / `partner`), `createdAt`, `status`, `data`, `crm`. Адаптер обязан использовать `Idempotency-Key` для исключения дублей, сохранять заявку в действующую CRM и уведомлять назначенного менеджера. Успех — HTTP 2xx. Ошибки видны в панели; предусмотрена повторная передача.

При отсутствии адаптера заявки сохраняются в подключённой базе для обработки командой. Это не считается доставкой в стороннюю CRM. При отсутствии базы формы переключаются на подготовку WhatsApp без ложного сообщения об отправке.

## Валюта

KZT — базовая валюта. Формула: `round(KZT × rubPerKzt × markup / rounding) × rounding`. Направление курса всегда «RUB за 1 KZT». В панели доступны ручной курс, коэффициент и шаг округления.

Для автоматического режима задайте `FX_API_URL`: утверждённый HTTPS-адаптер возвращает `{rubPerKzt: number, source: string, asOf: ISO-8601}`. Опциональный токен — `FX_API_TOKEN`. Курс обновляется при запросах витрины после истечения часа. Данные старше семи дней отклоняются; устаревший автоматический курс не используется для новых заказов. Без курса отображается запрос цены, а не выдуманная конвертация.

На Vercel страна определяется из доверенного `x-vercel-ip-country`. Ручной выбор KZT/RUB в браузере имеет приоритет и сохраняется. Региональные маршруты `/ru/catalog/...` подготовлены для российского рынка.

## SEO и аналитика

Build создаёт индексируемые HTML-страницы категорий и сервисных разделов, canonical, hreflang и robots. Сервер товарной страницы возвращает название, описание, характеристики и Product JSON-LD до выполнения JavaScript, только для опубликованных товаров. Несуществующий товар получает HTTP 404. Карта сайта включает опубликованные товары из базы. Системные страницы исключены из индексации.

События `solar:analytics`: `view_item`, `add_to_cart`, `order_submitted`, `partner_request_submitted`. События не содержат контактных данных. Подписка: `window.addEventListener('solar:analytics', event => { /* approved analytics adapter */ })`.

Изображение серии гибридных инверторов и технические документы взяты с официального сайта Deye; ссылки на источники находятся в `server/seed.ts`. Главный экран использует визуальное кадрирование исходного изображения средствами CSS, модель не перерисована.

## Проверки

`npm test`: публикация, безопасные URL, валюта, серверный пересчёт, валидация, авторизация, Origin, конфликт редакций, сохранение и идемпотентность заказа. Тесты используют изолированную `.test-data`, не создают реальные заявки и не вызывают CRM.

`npm run build`: TypeScript для frontend/API/tests, Vite, SEO generation. Дополнительно проверены мобильная верстка, корзина, сохранение избранного, сравнение, валидация и подготовка WhatsApp. Тестовые товары не публикуются.
